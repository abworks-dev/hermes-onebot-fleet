# P0：持久化业务准入与稳定主角色（v0.4.0）

**2026-10-19；本次仅实现源码、离线测试与文档，未更新线上插件、重载 Gateway、操作 QQ 或验收真实冻结。** 不增加自动轮号、强制保持登录、自动重新登录、人脸/解封或自动解除隔离。

背景与平台风险见[账号运维指南](qq-account-operations.md)，调查原址及证据局限见[信息来源](qq-account-sources.md)。这些控制减少误操作与误发送，不代表 QQ 授权，也不保证不受限。

## 三件事分别管理

- **业务准入**：持久化 `allowed / paused / quarantined / observing`，不能由在线恢复、定时器或重启自动放行。
- **传输观测**：现有身份校验、在线/健康检查仍独立运行。暂停不关闭 WebSocket，不注销 QQ，也不阻止 NapCat 自己的恢复机制。
- **主角色偏好**：持久化 sticky primary；不是轮号调度，也不是全群发言能力证明。CLI 不进行网络探测，状态中的 primary 可能暂时离线或被暂停，应结合准入与运行观测判断。

首次接入此版本时，**配置中的账号是管理员授权的初始集合，首次建立准入记录为 `allowed`**；未知账号不获准入。升级之前已经受限的账号不会被自动识别，管理员必须先审查配置和暂停/隔离需求，不要直接把旧配置上线。不存在自动封号分类、固定冷却期或自动风险评分。

## 状态与审计

| 命令动作 | 结果 | 注意 |
|---|---|---|
| `pause` | `paused` | 维护/人工暂停，不登录或退出 QQ |
| `quarantine` | `quarantined` | 隔离待人工处理，无定时释放 |
| `observe` | `observing` | 非隔离状态可转为观察，仍不承接业务 |
| `allow` | `allowed` | **唯一人工解除暂停/隔离/观察的准入动作**；不是自动恢复 |
| `promote` | 改变主角色偏好 | 必须已准入；不重新准入、不验证网络健康 |

隔离有锁存：`quarantined` 上执行 `pause/observe` 仍保持 `quarantined`，审计记录请求动作；观察应理解为人工复核过程，不能借此解除隔离。只有本人完成必要官方处理、管理员复核后才考虑 `allow`。这不要求持续登录 NapCat，也不承诺观察多久安全。

每次准入动作（包括重复动作）增加账号 revision；从配置移除账号也使旧 revision 失效。移除再添加、重新加载、重启均不会重置已有隔离状态。`promote` 不解除隔离，也不增加准入 revision。

操作审计保存时间、账号、动作、原因、状态/revision/主角色；查询最多返回最近 100 条，底层记录不自动清除。操作者是持有本机文件权限的管理员，**不是独立认证的远程管理员身份**；原因由管理员手写，严禁放入 Token、验证材料或消息正文。

## 本地管理命令

在仓库独立开发环境运行，不需要 QQ Token、不连接 QQ，不进入 Hermes 托管环境安装依赖：

```powershell
$env:PYTHONPATH = 'src'
# 指向该 profile 实际配置的 Fleet 消息账本；默认名称如下。
$state = '<profile>/plugin-data/onebot-fleet/onebot-fleet.sqlite3'

.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state
.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state --action audit

# 假号码，仅示范管理动作；写操作必须有账号、原因和 --confirm。
.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state --action pause --account 10001 --reason '人工复核' --confirm
.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state --action quarantine --account 10001 --reason '本人处理官方验证' --confirm

# 本人完成处理并经管理员复核之后，才可显式恢复准入。
.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state --action allow --account 10001 --reason '人工复核完成' --confirm
# 如确实需要换主，再单独执行；恢复准入本身不抢回正在工作的主号。
.\.venv\Scripts\python.exe -m hermes_onebot_fleet.cli accounts --state $state --action promote --account 10001 --reason '人工决定切换主角色' --confirm
```

命令要求现有消息账本和准入 sidecar 已存在；不负责初始化、绕过或重建准入。首次启动由新版适配器创建 sidecar。输入缺失、未知账号、状态文件结构错误、隔离账号升主均拒绝；无法读取状态不当作已放行。路径选择就是管理范围，CLI 不读取 profile 配置来替管理员推断目标，请核对账本路径与输出的 logical_id。写操作不需要重启，**后续业务门禁**读取已提交状态；它不是已在途操作的撤回命令。

## 主备行为变化

首次选主按配置 `priority`（小者优先，账号 ID 打破平局）选择已准入且健康的候选；随后保留当前主角色。只有当前主角色不再符合这些全局条件时，才从候选中降级选择备用并持久化。原高优先级号恢复健康或执行 `allow`，不会挤走仍合格的当前主角色。全部传输短暂不可用时保留最后偏好，避免恢复后按优先级重置。

群成员检查失败可以对该目标使用备用，但**单目标故障不改写全局主角色**。因此某条消息的实际发送号不一定等于全局 primary。这不包括目标级熔断、群禁言/风控诊断或发送探针；账号健康不证明每个目标都可发送。

手动 `promote` 仍受实际传输和目标检查约束，不保证离线账号立即发送。多操作并发时只承诺后续检查读取已提交状态，不提供跨机器选主或远端 QQ 栅栏。v0.2 历史“主→备→主”实测记录不是 v0.4 的默认回切策略。

## 门禁覆盖与不可撤回边界

1. **接收前**：一次读取管理状态与 revision，非 `allowed` 不进入新入站队列。
2. **交接 Hermes 前**：重新检查账号/revision、当前用户/群/逻辑空间/结构化 @。撤权旧任务记为 `denied`，不调用宿主。
3. **普通回复**：`reply_to` 必须匹配本插件已交接/交接中的原始入站及规范目标，且源账号准入 revision 仍有效；不把任意字符串、继承的 task context 当授权。
4. **选号与只读预检后**：只考虑已准入且身份健康的候选；跨 await 的暂停/再放行使旧 permit 失效。
5. **实际发送前**：持久化发送占位之后再校验源回复与所选号。若此时已撤销，保留确定未派发的失败 tombstone，不发送、不换号自动补发。
6. **后台发布**：publisher 复用同一发送路径；全池无准入路由且从未尝试发送时可保持 `pending`，不是伪造 `sent`。已有 `sent/unknown` 回执先返回原状态，不能因后来停号降回可重试的 pending。

暂停不会取消已经交给 Hermes 的模型/工具执行；必要时由管理员另行使用宿主的任务控制。后续回复会重新检查源入站准入。即使该源账号后来重新放行，旧任务仍因 revision 不符而不能发送。升级前无 revision 的队列/回复也拒绝，不能据此自动重跑模型或复制新发布 ID。

**最后一次已提交准入检查是本地 dispatch 的授权点；之后已经开始的网络请求不能撤回。** 暂停与派发竞态不能变成“所有在途请求已取消”的承诺。已派发后的 ACK、失败或不明结果照实入账；未知结果不跨账号重发，不宣称 exactly-once。

账号暂停不等于撤销 publisher 的已暂存业务意图；符合 TTL 的 `pending` 在有其他已准入路由时仍可能派发。需要整体停发时应停止业务提交并按批准的流程停用发布服务/所有账号，不能只停一个号。当前没有逐条取消 API；不要删账本或 tombstone 来取消/补发。

## 存储、升级与回滚

消息账本旁新增 `<账本文件名>.accounts.sqlite3`，只含管理/主角色/审计信息；不是 Hermes 内部 DB。它与消息账本、独占锁、发布账本一起按私密运行状态备份，不提交 Git，不通过删除文件解除隔离。文件权限是管理授权边界；同用户下 profile/venv 不是 OS 沙箱。

本轮没有自动部署。计划升级时先停止该测试 profile 的旧适配器，保存配置、旧插件、消息/发布账本和全部准入状态备份，检查旧任务与未知回执，再按原生 PM/插件流程装载经审查的新源码。`stage-plugin` 仍拒绝覆盖现有目录。共享 Gateway 的停用/加载范围需由管理员核对，不能靠启动第二个相同账号适配器接管。

降级至 v0.3 会失去本地准入门禁，旧版不知道这些隔离状态，**不能在仍需隔离的账号配置上直接回滚开流量**。先保持业务停止、人工收敛账号配置并复核运行版本；保留全部备份与 tombstone。不要为降级修改宿主内部数据库。
