# 个人 QQ / NapCat 账号运维指南

整理日期：**2026-10-19**。适用于本人合法控制的个人 QQ、获准使用的普通群聊与私聊。不覆盖 QQ 频道、自动加好友、入群、群管理或身份验证自动化。

> **交付状态：本文将既有只读调研整理为项目运维说明。P0 账号生命周期与稳定主备已实现源码和离线回归，不代表已部署，也未经真实 QQ 联调或线上故障验收。本文不授权自动轮号、强制登录、反复重登或解封操作。**
>
> 本文说明安全原则和状态概念；具体管理入口、持久化行为与离线验收以配套的[账号生命周期说明](<account-lifecycle.md>)为准，不在此预设 CLI 语法。证据原址、日期、版本和局限见[来源与证据边界](<qq-account-sources.md>)。

## 1. 先明确不能保证什么

- **号池不能消除平台规则风险。** 腾讯可读公开协议涉及未经授权的第三方工具、非人工发送与限制账号使用；该页面未给出更新日期，不能把它称为已核验的 2026 年最新版。[官方规则证据](<qq-account-sources.md#腾讯官方规则与处理入口>)
- **“身份验证信息已失效”不是唯一原因诊断。** 既有调研未找到腾讯对这句提示的可核验专项解释；仅凭提示不能认定是 NapCat 处罚、OneBot Token 过期、身份证到期或某一种实名问题。
- **不存在本项目可承诺的固定冷却期。** “四五天”“一周”只是部分用户经验，另有静置四十多小时后复发、七天解封后一登录再次受限的反例。
- **没有可靠证据证明解封后保持 NapCat 登录比停用更安全。** 登录观察是本人自愿承担风险的选择，不是默认要求，也不是“养号”方案。
- **多账号不等于高可用。** 同宿主多号可能一起异常；私聊、好友关系、群成员资格也不随账号自动迁移。QQ 以外应有状态记录和独立告警出口。
- **Fleet 停发不等于 NapCat 停止自动恢复。** 固定版本 v4.18.38 存在部分掉线事件后的 Worker 恢复路径。不能承诺上游没有自动重启或快速登录，也不能未经核验声称存在通用的“禁用全部自动重登”开关。[固定版本证据](<qq-account-sources.md#napcat-固定版本源码与项目文档>)

这些控制减少的是误恢复、重复发送、重试风暴和误操作，不是规避腾讯风控，也不构成平台授权。

## 2. 三个维度分别看，不用“在线”代替准入

| 维度 | 要回答的问题 | 不意味着什么 |
|---|---|---|
| 管理状态 | 管理员是否允许这个账号承接业务？ | 不能由网络状态、计时器或重启擅自改变 |
| 运行观测 | 连接是否建立、身份是否匹配、QQ 是否在线、信息何时取得？ | `online=true` 不证明每个群/私聊可发送，也不证明没有平台限制 |
| 业务角色 | 当前有效主号、备用，还是无可用角色？ | 优先级高不代表应立即抢回主角色 |

P0 运维使用下列管理状态概念；不是 QQ 官方账号状态，也不是对所有功能均已上线的声明：

| 状态 | 运维含义 | 恢复业务的要求 |
|---|---|---|
| `allowed`（已准入） | 管理员明确允许参与业务；仍须通过身份、健康、目标授权等检查 | 准入只是必要条件，不保证选中或发送成功 |
| `paused`（业务暂停） | 管理员暂停该账号业务，例如维护或等待复核 | 只能经显式人工操作重新准入 |
| `quarantined`（隔离待处理） | 明确限制、身份核验或人工判定需要隔离；不承接业务 | 本人先完成必要的官方处理，再由管理员复核；不得自动放行 |
| `observing`（观察但未准入） | 本人处理后观察、待复核；不承接业务，也不要求持续登录 NapCat | 观察时间或登录成功都不能自动变为 `allowed` |

**只有显式人工重新准入，才可从暂停、隔离或观察恢复业务资格。** 到期、WebSocket 重连、进程重启、`online=true` 或收到新消息，均不能替代人工放行。复核时间只是一条提醒，不是腾讯认可的恢复窗口。

推荐的人工处理顺序是：

```text
allowed → 人工暂停 → paused → observing（可选）→ 显式人工 allow → allowed
        → 明确限制 → quarantined（本人处理/人工观察期间仍隔离）→ 显式人工 allow → allowed
已有合格主号时，恢复准入不抢回主角色；如确需换主，再另行人工 promote
```

P0 的 `quarantined` 是锁存状态：对它执行 `pause/observe` 不解除隔离；人工观察可记在原因/运维记录中，只有显式 `allow` 恢复业务准入。这里的观察不要求保持登录 NapCat。

不要通过删改账号配置、删除本地状态、清缓存或重建身份来绕过已记录的隔离。运行数据、凭据与备份不得提交仓库。

## 3. 稳定主备：保持当前主号，不自动按优先级回切

P0 目标策略是 **sticky active primary（稳定当前主号）**：

1. 当前主号仍已准入并满足使用条件时，不因原高优先级账号恢复健康而自动换回。
2. 主号不可用时，只有已准入、身份与健康符合要求、目标也允许的备用号才有候选资格。
3. 原号恢复连接仅更新观测；若原先暂停或隔离，仍须人工重新准入。即使恢复准入，也不自动夺回当前主角色。
4. 涉及身份核验、冻结、反复异常或多号同时异常，优先人工评估是否暂停整个 QQ 业务；不要把号池变成跨号循环尝试器。
5. 不提供定时轮号、冷却到期自动放行、强制保持登录或自动解封策略。

仓库既有文档中的 v0.2 真实测试曾覆盖“主号服务停用 → 备用接管 → 原主恢复后回主”。那是**历史优先级回切行为的证据，不是 P0 目标策略，也不是本次升级验收结果**。停用 OneBot 监听服务的测试不等于 QQ 冻结、主机故障或全链路高可用测试。历史上下文见[架构与可靠性边界](<architecture.md>)；不要把它当作新版本自动回切承诺。

## 4. 日常使用清单

- 不把重要主号、支付或关键客户沟通的唯一账号当实验账号；专用号也仍有风险。仅使用本人合法控制、本人能够处理官方验证的账号。
- 每个账号使用独立运行目录，核对实际登录身份；避免同一账号多实例争抢登录。保护 Token、登录缓存、备份及本地账本，见[变量与存储说明](<variables.md>)。
- 仅服务授权用户和普通群，保留明确群内触发条件。不要为了健康探测主动发群消息、加好友、邀请或管理群。
- 连接、身份、QQ 在线和实际业务结果分别记录。接收正常不证明发送正常；某群失败也不自动等于全号冻结。
- 不把账号数量换算成可增加的总发送量；业务总量不能通过切号重置。平台没有公开可依赖的“免封阈值”。
- 保留业务 ID、去重与发送结果账本。重要状态不要只存于 QQ；QQ 故障时使用本地记录和独立告警渠道。
- 不采纳伪造设备、拦截检测、绕过人脸、代解封、买号或批量注册方案。不把清缓存、升降级或换设备当作默认恢复动作。

## 5. 遇到掉线、发送失败或验证提示

### 第一步：先止损，记录事实而不是猜原因

区分本地连接断开、QQ 明确离线、单群失败、私聊失败、身份核验提示、账号明确受限和原因未知。记录发生时间、账号本地别名、部署版本、观测来源及脱敏错误摘要；不从单一超时诊断封号，不把所有非零错误码都归为风控。

### 第二步：阻止该账号继续承接业务

对明确限制或需人工处置的账号执行隔离；维护可暂停。业务门禁应覆盖入站、新任务交接、排队后的重新检查、选号及发送前的最终检查，包括普通回复和发布入口。实际覆盖范围与验收见[账号生命周期说明](<account-lifecycle.md>)。

暂停不是撤回：已发出的请求可能仍完成；已经开始的模型任务也不等于可继续发送。对在途结果诚实记录“已发、失败或不明”，不要假称已全部取消。

### 第三步：判断备用是否真的能接管

| 现象 | 运维选择 |
|---|---|
| 单纯传输中断，有已准入且可服务目标的备用号 | 可按稳定主备策略降级；不是已发送消息的跨号重试许可 |
| 单群发送失败，其他业务仍正常 | 记录目标级故障，不凭此诊断全号受限；不要自动试发验证 |
| 明确冻结、身份核验或反复异常 | 保持隔离，本人处理；人工评估是否整体停发 |
| 同一环境多个账号同时异常 | 通过 QQ 之外告警，人工评估服务级暂停，避免逐个消耗备用号 |
| 整池不可用 | 明确报告不可用，不伪造发送成功，不自动登录补救 |

### 第四步：由本人在官方界面处理

使用最新官方手机 QQ 查看实际限制详情，按[QQ 官方解封入口](<https://accounts.qq.com/login/limit>)或客户端指引处理；身份核验参见[官方辅助身份验证说明](<https://accounts.qq.com/appeal>)。存在异议时参考[腾讯客服说明](<https://kf.qq.com/faq/161227QJJNJz161227EN32UN.html>)及实际页面的复审路径。不要照搬旧客服页中无关的删目录或关闭安全软件建议。

只由账号本人在可信官方界面提交所需材料，不自动申请解封，不循环刷新二维码或快速登录。Bot、插件、模型、代办服务不应接收人脸、证件或验证码；日志也无需保存这些验证资料。

### 第五步：登录恢复与业务恢复分开

- 本人完成处理或登录成功后，仍保留暂停/隔离，必要时进入不承接业务的观察状态。
- 可以选择暂不接入第三方客户端。若本人明确选择继续登录观察，先核对实际 NapCat 版本及恢复策略；这不是经证明更安全的做法。
- 管理员复核后显式重新准入，记录操作者、时间、原因和验证结论，不保存验证材料本身。恢复准入不自动升主。
- 不强制等固定天数，也不因等够天数自动放行；未消除的不确定性应继续显示为不确定。

## 6. 发送结果：不明就不能换号补发

- 已经尝试发送，随后超时、断线、取消或崩溃，可能是“已经发送但回执丢失”。记为 `unknown` / `uncertain`，查询原记录或人工核对，**不跨号重发同条消息**。
- 不通过新发布 ID、换账号或重新生成文本绕过去重。稳定发布 ID、不可变内容与保守账本语义仍然有效。
- 只有能够证明尚未进入任何实际发送 RPC 的“无可用路由”，才属于可保留待处理的情况；已发送后的拒绝也不是自动换号重试许可。
- 恢复服务不应集中倾倒积压或补发过期资讯；实际队列期限与预算按当前部署策略核对。
- `sent` 且有消息 ID 只表示 OneBot 确认，不代表收件人已读、所有群可达或端到端 exactly-once。

详细边界见[架构说明](<architecture.md>)、[后台任务运维](<cron.md>)和[权限说明](<permissions.md>)。

## 7. 上游控制与上线前检查

Fleet 业务暂停应独立于 NapCat 是否仍在线，但不代表能控制 QQ 客户端或 NapCat 的全部进程恢复。v4.18.38 源码中的约 3.5 秒和 60 秒是特定恢复分支的默认等待值，**不是账号冷却建议**。不同启动方式、版本、配置及部署管理器须单独核对。

上线前由管理员确认：

- [ ] 具体账号生命周期入口、鉴权、持久化、审计及所有业务门禁已通过离线测试。
- [ ] 暂停/隔离不会被到期、重连、重启、账号配置变动或健康恢复误清除。
- [ ] 原高优先级账号恢复不自动抢主，人工放行与人工升主明确分离。
- [ ] 模拟覆盖队列前后暂停、发送锁竞争、回执丢失、重启、多号异常与整池不可用；不以制造真实冻结验收。
- [ ] 已核对实际 NapCat 恢复能力，没有把“Fleet 不重登”误写成全链路保证。
- [ ] 已部署版本与回滚方式、QQ 以外的告警和人工责任人明确。若要真实联调，需另行逐项授权；本次文档和源码升级都不构成线上测试许可。

## 8. 后续能力不冒充 P0 已完成

目标级健康与熔断、服务/账号/目标统一预算、管理状态页、独立告警集成及长期可验证指标，属于后续设计与验收范围。除非有对应实现与测试证据，不因本文提及就宣称已具备。

个人 QQ 号池只能尽力降级。官方机器人也不是个人好友和普通群场景的无缝替代品；需要持续可用的重要业务，应另行评估合规渠道和独立通知方案。
