# QQ / NapCat 账号运维：来源与证据边界

整理及既有调研基准日期：**2026-10-19**。配套阅读：[个人 QQ / NapCat 账号运维指南](<qq-account-operations.md>)。

本文依据既有完整只读调研整理，保留其已记录的原始 URL、日期、固定版本和反例；**本次文档入库没有重新联网复核页面或新增真实 QQ 测试**。没有记录的日期、版本、提交哈希不作补写。本文不是网页全文存档，论坛仅作必要的事实摘要，不复制整帖或披露私人账号、验证资料及本地取证路径。

## 1. 如何解释证据

| 层级 | 能证明什么 | 不能证明什么 |
|---|---|---|
| 腾讯官方可读规则/处理页 | 所读正文的公开条款及官方处理指引 | 无更新日期时不能称为最新版；不能据通用条款确定某次提示的唯一原因 |
| NapCat 官方文档、固定版本源码 | 项目建议或该版本特定代码路径 | 不等于腾讯授权、账号安全认证，或每次故障都会执行该路径 |
| OneBot 规范 | 标准字段和接口语义 | 不保证实现正确，不提供腾讯风控结论 |
| 一手 issue / discussion / 用户原帖 | 有人报告过相应现象、操作与结果 | 不足以确定因果、成功率、通用恢复时长或当前版本仍存在旧缺陷 |
| 推测及单次成功经验 | 待验证线索 | 不应直接变成自动轮换、强制登录或恢复准入策略 |

阅读顺序：先确认来源层级，再核对日期/版本，最后检查反例与混杂因素。跨账号、跨版本的零散报告没有可比较分母，不可拼成“平均每周掉一次”“冷却七天有效”或“多号提高多少可用性”的统计结论。

## 腾讯官方规则与处理入口

### T1. 《QQ 软件许可及服务协议》：规则风险的一手来源

- 原址：<https://ti.qq.com/agreement/index.html>
- 日期/版本：既有调研于 **2026-10-19** 读取到正文；该可读页未公布更新日期。新规则中心当时仅取得页面外壳，故**不声称核验了 2026 年最新版全文**。
- 既有调研记录的相关条款：
  - **8.2.2(4)、8.2.2(6)**：涉及未经授权的第三方工具、插件挂接或登录、使用服务。
  - **8.2.3(3)**：涉及通过非人工、非手动方式发送信息。
  - **8.2.6**：自助解封应由本人按腾讯指定流程人工手动提交，不得通过软件、程序申请，也不得提交虚假资料。
  - **8.3.1**：腾讯可根据情况限制功能或中止、终止号码使用。
- 支持的结论：第三方接入与自动化存在规则风险；换号、低频、静置和暂未受限均不构成平台授权。恢复处理应由本人按官方流程完成。
- 局限：这些是可读正文的条款摘要，不是对某一账号受限原因的鉴定，也不是法律意见；条款现行效力及具体流程应以官方实际展示为准。

## NapCat 固定版本源码与项目文档

### N1. v4.18.38：部分掉线事件后的自动恢复路径

- 固定版本：**NapCat v4.18.38**；该版本发布日期未在既有调研中记录。
- Shell 事件处理：<https://github.com/NapNeko/NapCatQQ/blob/v4.18.38/packages/napcat-shell/base.ts#L851-L880>
- 恢复实现：<https://github.com/NapNeko/NapCatQQ/blob/v4.18.38/packages/napcat-core/helper/offline-recovery.ts>
- 既有调研核对的行为：
  1. 处理 `KickedOffLine` 与 `SelfOffline`。
  2. 恢复函数默认在被踢后约 **3.5 秒**触发重启；静默离线约等待 **60 秒**，如已自行在线则不重启。
  3. 有当前 Worker 内的防重复触发变量；不等于持久化账号隔离，也不等于跨重启的重登预算。
  4. Shell 重启/登录路径可能导致重新快速登录。
- 支持的结论：即使 Fleet 不发起登录，上游仍可能自动恢复。Fleet 的业务准入与 NapCat 进程/登录行为是不同控制边界。
- 必须保留的限制：不是所有冻结都必然进入这些分支，不能说它能自动解除限制；代码路径不证明某次真实部署已执行。**3.5 秒和 60 秒是源码默认等待值，不是推荐冷却期。**不能外推到所有版本、启动方式和管理器，也未据此核验一个通用的“禁用全部自动重登”开关。

这份固定版本证据比论坛对“客户端会不会自己重登”的猜测更强，但仍须核对实际部署。P0 暂停业务不能被写成已实现停止上游所有自动登录。

### N2. NapCat 官方安全文档：项目建议，不是平台授权

- 原址：<https://napneko.github.io/other/security>
- 日期：既有调研记录源文件最近相关提交为 **2025-09-21**；未记录提交哈希，页面链接也不是固定提交快照。
- 内容摘要：项目承认账号风险，建议隔离常用号；提及更换账号或设备可能改善频繁掉线。
- 支持：风险客观存在，不能把重要主号安全寄托在第三方接入上。
- 不支持：“解除后重新运行”“通常不频繁”等项目描述不保证每个账号适用，不证明换号或换设备必有效，更不是腾讯授权。本文不将这些建议转换成自动设备变更或跨号规避流程。

## OneBot 规范的边界

### O1. OneBot v11 `get_status`

- 原址：<https://github.com/botuniverse/onebot-11/blob/master/api/public.md#get_status-获取运行状态>
- 日期/版本：OneBot **v11** 文档，引用 `master` 可变分支；既有调研未固定提交，也未记录页面修订日期。
- 支持：`online` 可以是 `null`；`good` 是实现给出的总体状态。不能把 WebSocket 存活、`good` 或一次消息接收解释为全业务可用。
- 不支持：规范没有通用的腾讯冻结通知或风控结论。具体实现的字段、错误码和事件必须逐项核验。
- 发送确认也有限：消息 ID 是 OneBot 回执，不证明收件人已读或所有目标可达，更不产生跨账号的远端幂等保证。

- 局限：不能证明所有离线都有相同机制；更不能未经当前版本验证把旧缺陷写成 v4.18.38 的既定现状。

## 用户经验与反例：不能据此制定“养号公式”

### A1. Discussion #1888：清理本地目录后的成败并存

- 原址：<https://github.com/NapNeko/NapCatQQ/discussions/1888>
- 日期：首帖 **2026-06-08**，后续包含 **2026-06-12** 的失败复现以及 7 月、10 月的复发报告。报告涉及版本未完整记录。
- 正向经验：有人称清理本地目录后近一周未掉。
- 同帖反例：也有人照做仍很快被踢。
- 混杂因素：目录变化可能伴随重启、重新登录、版本/账号状态或观察时段变化；没有对照，不能隔离每一因素的效果。“风险画像清零”是用户猜测，不是已证实机理。
- 运维采用：保留为问题线索，不提供删目录教程，不自动清缓存，不据此解除隔离。

### A2. NapCat #2079：同宿主多账号同时异常，也有不同表现

- 原址：<https://github.com/NapNeko/NapCatQQ/issues/2079>
- issue 日期：**2026-09-30 起**；首报环境 **NapCat v4.18.28 / QQ 3.2.30 / Docker**。相关评论精确日期及各账号版本未在既有调研中逐一记录，不能把首报版本套用到整帖。
- 报告：同宿主多个账号同时需要重登；另有账号表现不同的反例。
- 支持：多个账号不能假定为独立故障域；需考虑共同环境和服务级暂停。
- 混杂/局限：共享宿主、网络、版本、部署方式、账号历史与使用量可能同时变化；不能推导腾讯具体 IP 关联算法，也不能证明所有同宿主账号必定一起受限。

### A3. LINUX DO：四五天/一周的正向经验

- 原址：<https://linux.do/t/topic/2053304?page=2>
- 相关讨论日期：**2026-06-03 / 2026-06-04**。具体 NapCat/QQ 版本未在既有调研中记录。
- 报告：有“只登录 NapCat 挂四五天”和“一周后正常”的普通用户说法。

### A4. LINUX DO：静置或解封后仍复发的反例

- 原址：<https://linux.do/t/topic/2185106>
- 日期：**2026-05-15**。具体版本未在既有调研中记录。
- 报告：有静置四十多小时后只稳定一天、七天解封后一登录再次受限的情况。

- 局限：反例同样是用户报告，不能反推“所有静置都无效”“保持登录一定更危险”或计算失败率。正反两类报告共同否定的是通用保证，而不是确立另一种必胜方案。

## 2. 争议说法与可采用结论

| 说法 | 综合证据判断 | 项目采用方式 |
|---|---|---|
| 身份验证提示说明唯一确定的封控原因 | T2 存在专项解释缺口，C1 仅为案例 | 原因未知则记录未知；由本人按官方提示核实 |
| 号池可以保证始终在线 | A2 有共同故障报告，私聊/好友/群资格各自独立 | 只承诺尽力降级，不宣称 HA |
| 冷却四五天或一周就可自动恢复 | A3 没有对照，A4 提供复发反例 | 不设平台认证冷却期，到期仅提醒人工复核 |
| 解封后必须继续挂 NapCat 才安全 | 没有可靠比较证据，N1 还提示上游恢复路径 | 不强制保持登录，不把登录观察当恢复资格 |
| 换号、清缓存、换设备或升降级能根治 | N2 是建议，A1 成败并存且因素混杂 | 不自动执行，不提供反检测/身份绕过教程 |
| Fleet 不发起登录，整条链路就不重登 | N1 固定版本存在部分自动恢复路径 | 分别核对 Fleet 业务门禁和上游进程/登录行为 |
| 在线或收到消息就等于所有业务可用 | O1、C2、C3 均不支持 | 分开记录管理准入、观测和目标能力 |

## 3. 项目内证据与当前交付状态

- **既有源码审阅基线**：`f79e35f7e17bc639a4d0898632f52b55f1a1d95e`。既有调研指出该基线以健康与优先级选号，缺少持久化人工隔离和稳定当前主角色；这是升级动机，不是对 P0 完成后的判断。
- **历史真实测试**：[架构说明](<architecture.md>)记录 2026-10-18 的 v0.2 系列“主/备/主”行为，每轮 3 条真实消息、3 次交接和 3 次发送，未出现不明记录。测试故障是停用主号 OneBot 服务，不是冻结 QQ、杀死 QQ 进程或主机故障；历史自动优先级回主**不再是 P0 目标策略**。
- **v0.3 窄范围验收**：同一[架构说明](<architecture.md>)记录独立 worker、发布回执及重复 ID 查询等局部验证；备用号退出后额外双入口故障测试暂停。这些不能用来证明当前号池随时可用，更不能证明账号生命周期升级已部署。
- **本轮 P0**：账号准入、人工隔离、全入口业务门禁与 sticky active primary 已实现源码和离线回归；**未部署、未做真实 QQ 联调或线上故障验收**。管理入口与离线验收以[账号生命周期说明](<account-lifecycle.md>)为准；这些工程测试不是账号安全或平台授权证据。
- **保留的安全边界**：发送不明不跨号重试、稳定发布 ID 与去重不因恢复账号而失效。工程实现边界参见[架构](<architecture.md>)、[权限](<permissions.md>)、[验证地图](<tests.md>)。
